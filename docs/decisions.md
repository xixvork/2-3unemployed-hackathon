# Troubles and Solutions

## Why this file exists

У завданні окремо підкреслено цінність деталізації проблеми та прийнятих рішень.
Цей документ фіксує ймовірні технічні проблеми, які реально виникають у такому проєкті, та наші рішення.

## Troubles and solutions

1. Trouble: Невизначеність API-контракту між фронтом і бекендом.
Solution: Зафіксували контракт для `GET /orders`, `POST /orders`, `POST /orders/import` у `docs/api.md` із прикладами request/response.

2. Trouble: Ризик неточних розрахунків податку через floating-point.
Solution: Для money/tax полів у контракті прийняли формат рядків (`"49.99"`, `"0.08875"`), а не `number`.

3. Trouble: Невизначений формат CSV-імпорту (можливі різні колонки/порядок).
Solution: Домовилися про мінімальний набір колонок (`latitude`, `longitude`, `subtotal`, `timestamp`) і валідацію кожного рядка.

4. Trouble: Частина рядків у CSV може бути невалідною.
Solution: Імпорт зробили частково толерантним: валідні рядки створюються, помилки повертаються у `errors` з номером рядка та кодом.

5. Trouble: Вимога не використовувати runtime-звернення до зовнішніх API для податку.
Solution: Розрахунок податку виконується на локальних даних ставок.

6. Trouble: Нечіткість у постановці щодо обов'язковості додаткових полів (наприклад, `jurisdictions`).
Solution: Зафіксували їх як бажані/bonus поля та винесли рішення в документацію, щоб уникнути суперечностей у команді.

7. Trouble: Різний темп роботи над фронтом і бекендом.
Solution: Пішли від API-first підходу: спочатку контракт і приклади JSON, потім імплементація.

8. Trouble: Невизначені граничні кейси валідації (`latitude/longitude`, порожній CSV, невалідний timestamp).
Solution: Додали явні правила валідації та стандартний error-contract для всіх endpoint-ів.
